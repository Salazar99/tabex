# Tabex: STL Similarity Metric Calculator

[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](./LICENSE)
[![Python 3.10+](https://img.shields.io/badge/python-3.10+-blue.svg)](https://www.python.org/downloads/)

**Tabex** is the official repository for the Signal Temporal Logic (STL)
similarity metric calculator. It computes each formula's **signal space** — the
set of signals satisfying it, as a union of boxes — reduces both to a canonical
form, and scores their overlap.

---

## ⚡ Quick Start

```bash
git clone https://github.com/Salazar99/tabex.git
cd tabex
pip install pydot pytest matplotlib

python run_similarity.py "F[0,2] x>0" "G[0,2] x>0"   # run the tool
pytest -q                                             # run the test suite
```

No Rust, no Z3, no environment variable: the default path is pure Python.
Those are needed only for the optional `--via tableau` route below.
See [Testing](#-testing) for the three-tier suite (fast/integration/slow).

### Which path runs

There are two ways to compute a signal space, and they agree:

| | `--via definition` (default) | `--via tableau` |
|---|---|---|
| how | structural recursion on the formula | extracted from `stlsat`'s tableau |
| status | **proved** correct — [FORMAL_PROOFS.md](./FORMAL_PROOFS.md) Theorem A | *cross-checked* against the definition, not trusted |
| needs | Python only | Rust + Z3 |
| speed | slower on wide formulas | fast |

The definition is the default because it is the one the proofs are about.
The tableau is kept because it scales further and is the only route that can
read a hand-written `.dot`. `tests/test_reference_semantics.py` compares them on
every connective.

When it matters: the ten manual benchmark pairs take **~93 s** denotationally
and are near-instant via the tableau — almost all of the difference is the two
four-variable pairs. Reach for `--via tableau` when formulas get wide.

## 📖 Worked example

[EXAMPLE.md](./EXAMPLE.md) runs three pairs through **every** stage — string →
AST → boxes → signal space → breakpoints → fine arrangement → canonical cells →
`Point_sim_D` → `Path_sim` → `G` — with a figure per stage and every
intermediate value printed.

| | pair | what it shows | score |
|---|---|---|---|
| 1 | `G[0,1](x>0) && F[0,1](y<3)` vs `(x>0) U[0,1] (y<3)` | two variables, `G` and `U`; φ strictly inside θ, so the two directions disagree (1.0 and 0.9) | 0.95 |
| 2 | `F[0,1]((x>0 && x<2) \|\| (x>4 && x<6))` vs `F[0,1](x>1 && x<5)` | a variable bounded on both sides, a disjunction becoming four paths, and the Jaccard branch of `Point_sim_D` firing | 0.4159 |
| 3 | the L-shape, cut two ways | two *different* decompositions of one region canonicalising to the *same* cells: 0.75 before, 1.0 after | 1.0 |

Regenerate any part's figures and its numeric trace with `plot_pipeline.py`:

```bash
python3 plot_pipeline.py 'G[0,1](x>0) && F[0,1](y<3)' '(x>0) U[0,1] (y<3)' \
        -o figures/example
```

It works on any pair, and asserts its own arithmetic against the metric before
writing. `plot_signal_space.py` draws just the signal space (`--canonical` for
the cells the metric actually compares).

## 🚀 Installation

### Requirements

  * **OS**: Tested on Ubuntu 22.04.5 LTS.
  * **Python**: Tested with Python \> 3.10.
  * **Rust** ([rustup.rs](https://rustup.rs/)) and the **Z3** executable —
    *only* for `--via tableau`, the integration tests, and
    `verify_semantics.py`. The default path needs neither.

> **Note**: `stlsat` does not need compiling beforehand; it is run with
> `cargo run`, which builds it automatically on first use.

### Setup

```bash
git clone https://github.com/Salazar99/tabex.git
cd tabex
pip install pydot pytest matplotlib
```

  * **pydot**: required on every path — `parse_graph.py` imports it at module
    scope, and the metric imports `parse_graph` for its interval algebra. Only
    the tableau route actually parses `.dot`.
  * **pytest**: only needed to run the test suite.
  * **matplotlib**: only needed to regenerate the worked example's figures
    (`plot_pipeline.py`, `plot_signal_space.py`). The metric itself never
    imports it.

### `TABEX_ROOT`

Needed only to locate `m_stlsat/` for the tableau route. Unset, it defaults to
`~/tabex`; `--tabex-root` overrides it per invocation.

```bash
export TABEX_ROOT=$(pwd)
```

## 🛠 Usage

### 1\. One-Command Execution

```bash
python run_similarity.py "First_formula" "Second_formula" \
    [--D VALUE] [--via definition|tableau] [--save-volumes] [--tabex-root PATH]
```

  * **--D**: (Optional) The **domain**: the largest magnitude any monitored
    variable is assumed to take, which the metric truncates every constraint
    to before comparing them. See [Choosing D](#choosing-d).
  * **--via**: `definition` (default) or `tableau` — see
    [Which path runs](#which-path-runs).
  * **--save-volumes**: (Optional) Saves each formula's signal space to a
    `.json` file, computed by the same route as the score.
  * **--tabex-root**: Override `$TABEX_ROOT` (`--via tableau` only).

#### Choosing D

`D` is a user parameter, and it has a hard requirement: it must **exceed every
constant occurring in either formula**.

```bash
python run_similarity.py "x>2" "x>5"            # D derived as 5 + 1 = 6  -> 0.25
python run_similarity.py "x>2" "x>5" --D 100    # 95/98 ~ 0.9694
python run_similarity.py "x>2" "x>5" --D 21/2   # exact rationals accepted
python run_similarity.py "x>2" "x>5" --D 3      # refused: needs D > 5
```

Omit it and it is derived as `max|constant| + 1`. Pass one at or below that
bound and the run fails, naming the minimum — it is **not** silently raised to
a working value, because too small a `D` truncates two genuinely overlapping
unbounded constraints into disjoint ones and changes the score without saying
so. A score is only meaningful for a `D` that was actually well formed.

Above the bound, `D` is a sensitivity knob. Two constraints sharing an
unbounded tail, like `x>2` and `x>5`, differ only by a finite offset: the
larger the `D`, the more the shared tail dominates and the closer the score
gets to 1 (`0.25` at `D=6`, `0.9694` at `D=100`). Smaller `D` makes that offset
matter more. Values are read exactly — `10`, `10.5` and `21/2` all work, and no
binary64 rounding enters the metric.

Prefer typing formulas interactively instead of shell-quoting them? Run:

```bash
python similarity_check.py
```

It prompts for a first formula, a second formula and a `D` (blank for the
derived one), prints the similarity score, and loops so you can run more
comparisons without restarting. A refused `D` is reported without ending the
session. Type `quit` (or `exit`) at any prompt to leave.

### 2\. Metric Only

`similarity/stl_similarity.py` has its own CLI, taking formula strings
directly:

```bash
python similarity/stl_similarity.py "First_formula" "Second_formula" [--D VALUE] [--via WHICH]
```

  * **--D**: (Optional) Truncation window for `Point_sim_D`
    (Eq. `PointSimD`); auto-derived from the two formulas' constants if
    omitted. Same rules as above — see [Choosing D](#choosing-d).

### 3\. Signal Space Generation

Denotationally, which is what the default path does:

```python
from reference_semantics import parse, signal_space, variables

tree = parse("G[0,2] x > 0")
paths = signal_space(tree, sorted(variables(tree)), horizon=tree.horizon())
```

Or from a tableau. `parse_graph.py` turns a stlsat tableau into a set of
standardized, feasible `Path`s (Algorithm 1), reading an existing `.dot` or
generating one by calling `stlsat`:

```bash
python parse_graph.py graph_examples/graph_G.dot     # from an existing tableau
python parse_graph.py --formula "G[0,2] x > 0"       # runs stlsat for you
```

Optional flags:

* **--tabex-root**: Override `$TABEX_ROOT` (default: `~/tabex`).
* **--save-dot**: Keep the intermediate tableau `.dot` for inspection.

As a library:

```python
from parse_graph import generate_signal_space_from_formula

paths = generate_signal_space_from_formula("F[0,2] x >= 0")
```

### 4\. Canonicalization (`similarity/canon.py`)

Two equivalent formulas can decompose the same region into differently-shaped
boxes, which understates their similarity if the boxes are compared directly.
`canonicalize()` is **unary** — it depends only on the region a formula's own
paths cover, never on the comparison partner — and reduces that region to a
canonical cell list in three steps:

1. **Breakpoints.** Pool the finite endpoints the formula's own boxes use, per
   axis (`_breakpoints`).
2. **The fine arrangement.** Cut every box at those breakpoints, emitting the
   degenerate point slab `[b,b]` alongside the open spans, so the atoms
   `(-∞,b₁), [b₁,b₁], (b₁,b₂), …` genuinely **partition** rather than merely
   cover. Without the point slabs, `x>=1 && y>-1` and `x>1 && y>=-1` produce
   cells that overlap on their interiors while each owns a different boundary
   sliver (`_fine_cells`, `_cut_piece`).
3. **The coarse product grid.** Per axis, and once, take the maximal runs of
   adjacent atoms carrying the same cross-section (`_axis_partition`); the
   canonical cells are the images of the fine cells in the product of those
   runs (`_slab_of`).

Step 3 is a **product grid, not a greedy merge**, and that is the whole point:
coalescing cells pairwise is not confluent — on an L-shaped region, merging `x`
first and `y` first give two different, both minimal, answers, so a "canonical"
form built that way would depend on axis order. Per-axis runs depend on no
traversal order, so their product is well defined. Holes need no special case:
`(x<1)||(x>1)` simply has no `[1,1]` atom, and two atoms open at `1` do not
touch.

Because the runs are determined by the region alone, two decompositions of one
region canonicalize to the identical cell list — so equivalent formulas score
`1.0`. That is [FORMAL_PROOFS.md](./FORMAL_PROOFS.md) Theorem B.

`build_aligned_volumes()` in `similarity/stl_similarity.py` wires this in before
comparison, so `run_similarity.py`, `similarity_check.py` and the metric's own
CLI all canonicalize automatically. `compute_similarity()` stays pure math over
whatever two path lists it is given, so calling it directly on volumes from
`build_volume_from_paths()` is possible but skips the guarantee.

```python
from similarity.canon import canonicalize

canonical1, canonical2 = canonicalize(paths1), canonicalize(paths2)
```

## 🧩 Supported fragment

### Why there is a fragment at all

A signal space is a **union of boxes**: per instant, per variable, a union of
intervals. That representation is what makes a canonical form possible — a
canonical decomposition needs axis-aligned cells — and it is also exactly what
decides the fragment. A constraint is representable iff it cuts each variable's
axis *independently*.

`x > 5` is an interval. `x > y` is a half-plane, and no union of boxes equals
it. So the boundary below is not an implementation shortcut you could paper
over; it is where the geometry stops working.

[**PROOF.md**](./PROOF.md) is the narrative account — what is proved, what is
only validated, and what a counterexample hunt over ~1,800 regions did and did
not find. [**FORMAL_PROOFS.md**](./FORMAL_PROOFS.md) is the mathematics with the
implementation in view. [**proofs.tex**](./proofs.tex) develops the same two
theorems for a reader without the repository; it deliberately differs, defining
the fine cells, the runs and the canonical form by the properties that
characterise them rather than by the steps that compute them.

### Supported

```
formula  ::= atom | true | false
           | !formula | formula && formula | formula || formula
           | formula -> formula
           | F[a,b] formula | G[a,b] formula | formula U[a,b] formula
atom     ::= variable op constant        op ∈ { <  <=  >  >=  ==  != }
constant ::= integer | decimal | rational          e.g. 5, -2, 1.5, 3/2
```

`!` and `->` are rewritten away before evaluation: the fragment proper is in
negation normal form, and negation is an operation on formulas rather than a
connective.

Constants may be **any rational** — `1/3`, `0.1` and integers past `2**53`
included. Interval endpoints are exact `Fraction`s, never binary64, because
rounding a constant would make the region denote a different set of reals than
the formula does, and could collapse two distinct endpoints onto one — which is
what the canonical form's proof forbids. Arithmetic on endpoints happens only in
the final Jaccard measure, computed exactly and cast to `float` once, at the
end. See [FORMAL_PROOFS.md §0.1](./FORMAL_PROOFS.md).

Temporal operators nest freely. Two rules are surprising enough to state, and
both are pinned by tests:

- **`U` includes its witness — a deliberate definition, not textbook STL.** The
  invariant is required up to *and including* the witness instant, not on the
  half-open `[t, witness)`, so `x>0 U[0,0] y>3` is `x>0 ∧ y>3` and not `y>3`.
  Equivalently `φ U ψ` here is `φ U_textbook (φ ∧ ψ)`. It is TABEX's convention,
  fixed in `reference_semantics.py` and in both proof documents, chosen because
  it costs nothing to prove and because stlsat's tableau already computes it —
  so the two paths agree without adaptation. Reasoning in
  [PROOF.md §2.4](./PROOF.md); pinned by
  `tests/test_reference_semantics.py::test_until_includes_its_witness` and
  `tests/test_stl_similarity.py::test_until_semantics`.
- **A nested window is relative.** The outermost interval is absolute and
  anything below it is relative to the operator above, so `G[1,1] G[1,2] P`
  requires `P` on `[2,3]` and asserts nothing at `t=1`.
  (`tests/test_semantics_examples.py::test_a_nested_temporal_window_is_relative_not_absolute`)

### Not supported

| shape | example | why |
|---|---|---|
| relation between variables | `x > y` | a half-plane, not a box |
| arithmetic terms | `x + y > 0`, `x - 1 > 0` | not a box |
| absolute value | `\|x\| > 1` | not a box |
| bare boolean atom | `p` | not a real-valued signal |
| chained comparison | `0<x<2` | an atom carries exactly one operator — write the conjunction, `x>0 && x<2` |
| release | `formula R[a,b] formula` | no `Release` node in the denotational fragment |

Each raises `UnsupportedFormula`, naming the offending label and the instant.
**It does not return an empty or unconstrained region** — silently widening a
formula it cannot represent is what would produce a confident, wrong score.

Release is the one row that is not a geometric limit: `--via tableau` does
handle `R[a,b]`, because stlsat rewrites it into `F`/`U`/`G` before the tableau
is built. It is unsupported on the default path only.

Supporting the other rows needs a representation richer than per-variable
interval unions — a design change rather than a parsing fix.

## 🧪 Testing

```bash
# Fast: unit tests + golden-output tests over graph_examples/*.dot (no Rust/Z3)
pytest -q

# Integration: calls the real stlsat binary via `cargo run`, and cross-checks
# the tableau against the denotational definition
export TABEX_ROOT=$(pwd)
pytest -q -m integration

# Slow: full tree build over the ~4.3MB graph_G_U.dot fixture, opt-in
pytest -q -m slow
```

`tests/test_dot_examples.py` and `test_formula_to_signal_space.py` are
regression tests (golden JSON snapshots — they catch *changes*, not necessarily
*bugs*). `tests/test_semantics_examples.py` instead checks output against the
actual STL meaning of each formula (`G[0,2] x>0` requiring `x>0` at every
instant, `F[0,2] x>=0` partitioning into disjoint earliest-witness paths), with
the reasoning in each test's docstring — that is the file to read if you want to
know *why* a signal space is correct, not just that it has not changed.
`tests/test_reference_semantics.py` holds the differential tests that keep the
tableau honest against the definition.

### Randomised verification

Three scripts sample far more cases than the fixed suite can, and are what the
correctness of the signal space actually rests on. Only `verify_semantics.py`
needs `cargo`/`z3` — it is the one that exercises the tableau.

```bash
python verify_semantics.py               # region == the formula's real semantics
python verify_semantics.py --boundary    # ... with values exactly ON the bounds
python verify_equivalence.py             # equivalent formulas score G = 1
python verify_canon.py                   # canon.py is lossless and canonical
```

`verify_semantics.py` is the ground truth: it evaluates each random formula with
its own small STL interpreter and compares that verdict against membership in
the extracted region, so it catches over- and under-approximation that
equivalence testing alone cannot see. **Run it with `--boundary`** — sampling
exactly on the integer bounds is what proves endpoint openness is handled, and
is what a closed-only interval representation can never pass.

It generates **nested** temporal operators (`--max-nesting`, default 2, about a
quarter of the formulas). That matters because the two levels of a tableau label
are anchored differently: an inner operator is rebased only when the outer one
unfolds, so in an un-unfolded label the outermost window is absolute while
anything below it is still relative. `G[1,1] G[1,2] P` therefore requires `P` on
`[2,3]` and asserts nothing at `t=1`. Every single-level test passes whichever
way you read that, so only the nested sweep pins it down.

`U` is covered too (about 30% of generated formulas contain one; `--no-until`
turns it off to isolate a failure), under the witness-inclusive reading
described above.

`verify_equivalence.py` generates pairs that are equivalent *by construction* —
a random formula and a meaning-preserving rewrite of it — so it never has to ask
anything whether two formulas are equivalent.

### On stlsat's verdict

The tableau path does not read stlsat's `Tableau result:` line.
`prune_incomplete()` derives emptiness from the graph instead: in a fully
unrolled tableau every leaf carries atoms only (`graph_G.dot` ends at `x > 0`,
`graph_U.dot` at `x > 0, y > 3`), so a leaf still naming `F`/`G`/`U` is a branch
stlsat stopped expanding — normally one it rejected, which is exactly what an
unsatisfiable formula needs. Extracting a partial constraint from such an
unfinished node would silently under-constrain the region.
